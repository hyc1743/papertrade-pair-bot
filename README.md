# Papertrade 实时 LP 动态对冲与质押脚本

本仓库是脱敏代码副本，不含实际钱包私钥、Bark 设备地址、账户数据库、运行日志或备份。运行前请自行填写本地 `.env`；不要将真实凭据或 `data/` 提交到 GitHub。测试使用固定测试钱包，不关联实际账户。

面向两个已开设、已入金的账户，当前模板按每个账户 500 USDC 配置。实时读取 LP、支付队列、铸币曲线及账户状态，开仓前选择策略；确认 PAPER 到账后立即尝试质押，独立监控真实 USDC 分配（默认不自动领取）。

## 1. 配置与运行

需要 Node.js 24+；部分边缘节点的公开前端资源读取会回退到 `curl`。

```bash
cd papertrade-pair-bot
npm ci
cp .env.example .env
cp config.example.json config.json
```

新模板已设置：每边保证金上限 333.33U、每钱包资金上限 500U、目标单边名义本金 10,000U、自动匹配杠杆、动态 LP 策略、自动质押，默认不自动领取分红。两钱包均有 500U 可交易现金时，整数杠杆取 31 倍，实际每边保证金约 322.58U，留下约 177.42U 非本轮保证金。自动杠杆范围为 1–50 倍，要求平仓目标之外至少 50 bps 强平缓冲。`maxNetLossUsdc: null` 关闭累计净损耗停止条件，不代表会忽略余额和强平距离。

保证金利用率 66.67%、50 倍杠杆上限和 50 bps 缓冲是脚本的配置选择，不是官方规定或收益最优证明。相比旧 300U 模板，提高保证金、降低杠杆，而不提高名义敞口；同样价格变动下的美元盈亏和铸币估计不会因为保证金增加而同比增加。

在本机设置环境变量：

```bash
export PAPERTRADE_WALLET_A_PRIVATE_KEY='0x你的钱包A私钥'
export PAPERTRADE_WALLET_B_PRIVATE_KEY='0x你的钱包B私钥'
```

或者在 `.env` 填入这两个变量，使用 Node.js 的 `--env-file=.env` 加载（不用 `source`）：

```bash
chmod 600 .env config.json
node --env-file=.env --import tsx src/cli.ts preflight --config config.json
```

```bash
# 只读检查，不签署授权或交易
npm run cli -- preflight
# 先累计交易一轮，完成后继续质押/分红监控
npm run cli -- run --live --max-rounds 1
# 按配置持续运行
npm run cli -- run --live
# 仅质押和领取，不开仓、不注册交易 session
npm run cli -- rewards --live
npm run cli -- status
npm run cli -- report
npm run cli -- stop
```

`rewards --live` 不接管未完成的交易仓位；有脚本仓位先用 `run --live` 恢复。两模式共用进程锁，不可同时运行。`stop`、`Ctrl+C`、`SIGTERM` 停止全部新操作并退出脚本存量仓位；官方暂停平仓或网络断开时保留状态等待。

### 等待官方开放后自动进入实盘

已经封装一键启动，使用 `.env` 中的钱包私钥和 `config.example.json` 中的预定策略，**固定开放日为 2026-10-10 UTC 14:00:00**，不按运行当天推算日期：

```bash
cd papertrade-pair-bot
npm start
```

提前检查时间是 **2026-10-10 UTC 13:59:57**（北京时间 21:59:57），最早交易时间为北京时间 22:00:00，同时必须确认官方实际允许交易。提前运行会等待，开放延迟则继续检查；如果在该时间之后才启动，会立即检查，不自动改为第二天。

`npm start` 是实盘启动，条件满足后自动开平仓及质押；分红领取由 `autoClaim` 控制，当前模板为 `false`，不再请求交互确认。不要同时运行第二个进程。保持终端打开；另一终端用 `npm run bot:status` 查看状态，`npm run bot:checkpoint` 只读查看断点，`npm run bot:stop` 请求停止新操作并退出脚本持仓。修改开放日期时需要修改 `package.json` 的 `start` 命令，或使用下面的显式命令；一键命令中的日期优先于配置。

以下命令由你在本机执行。日期必须替换为实际开放日；这里明确使用 **2026-10-10 UTC 14:00**（北京时间当天 22:00），不会自动顺延到次日。日期已过时，会立即检查是否允许交易，而不是再等待一天。

```bash
# 使用现有模板；从 .env 加载私钥，不在命令行填写私钥
env -u PAPERTRADE_WALLET_A_PRIVATE_KEY -u PAPERTRADE_WALLET_B_PRIVATE_KEY \
  node --env-file=.env --import tsx src/cli.ts run --live \
  --config config.example.json --opening-at 2026-10-10T14:00:00Z
```

也可在自己的 `config.json` 中设置 `openingAtUtc: "2026-10-10T14:00:00Z"`、`openingCheckLeadMs: 3000`；CLI 时间优先。省略时间且配置为 `null` 时，保持原来的立即检查模式。

- 启动后连接账户并读取 LP，**13:59:57 UTC 前不轮询交易入口或提交新的交易授权**（已有脚本持仓的恢复不受定时限制）。
- 提前 3 秒开始检查官方状态，允许注册交易 session；此阶段不新开仓、不质押、不领取。授权确认可能晚于开放时刻。
- 最早 14:00:00 UTC 之后，用开放时刻之后发起的新状态读取确认官方开仓和平仓入口、市场及策略条件可用，再自动开仓。官方延迟开放则持续等待；只读检查按 `pollIntervalMs`（默认 1 秒）执行，网络超时或限频会延后。
- 价格达到本轮策略阈值才平仓；不会用反复开平仓来探测入口。
- 当前模板 `openTimeoutMs: null`：两边都未成交时，不再因为排队超过 30 秒就退出；每 5 秒输出 `opening_wait`。新签署的开仓请求有效期为 3600 秒（`openIntentTtlSeconds`）；已提交的旧请求维持原截止时间。过期后确认 nonce 未使用、没有持仓／相关待处理请求且账本匹配，或旧请求已明确取消，才重新检查 LP、余额、行情与官方状态并重试。不会每秒签署一份重复订单。未知归属、明确的永久拒绝、停止请求或数据故障仍会阻止重试。
- 一侧成交后仍保留 `hedgeTimeoutMs: 30000`：从首次成交时间计算，另一侧 30 秒内没有形成完整对冲，就撤销未完成请求并退出已成交侧。无限排队等待不等于无限持有单边仓位。
- 只有双方开仓都被明确以 `intake_action_paused` / `rate_limited` 暂时拒绝、确认无持仓或待处理开仓时，才退避后重新检查并尝试。遵守 Retry-After；这些无成交尝试仍计入配置的累计轮数上限。模板的轮数上限为 `null`。
- 请求结果未知不盲目换 nonce 重发。开仓使用单独的 3600 秒有效期；平仓、授权和奖励请求仍默认 60 秒（`intentTtlSeconds`）。过期须以链索引和相应证据确认，而不是只看本机时钟。**平仓没有本地等待时限，也不会因超时、排队或 HTTP 响应丢失而调用取消接口**；`queued` / `unknown` 持续对账，每个钱包每 5 秒输出 `closing_wait`。只有确认旧请求已经结束、且仓位仍存在，才重新提交；若旧请求仍在官方待处理列表中，不重复提交。单边成交异常执行恢复退出流程并停止新交易，不盲目补仓。平仓请求明确失败时沿用至少 15 秒退避，同时遵守更长的 Retry-After。
- 时间门槛不阻碍存量平仓、恢复或停止。定时只约束新开仓，不承诺某一秒成交。

保持终端运行。另一个终端可查看或停止（下列命令不会读取私钥）：

```bash
node --import tsx src/cli.ts status --state-dir ./data
node --import tsx src/cli.ts stop --state-dir ./data
```

## 2. 动态策略

当前 `config.example.json` 使用 `lpAccumulating`：两个钱包都没有质押时，按实时铸币曲线选取**每个钱包各自两次亏损侧结算后预计达到最低质押量 105%** 的最小安全阈值，下限 15 bps；PAPER 不能在这两个钱包之间划转，因此从不合并 A、B 余额。策略报告逐钱包列出官方最低质押量、当前缺口、预计亏损次数和预计累积量。任一钱包实际到账达到官方最低质押量就立即独立质押，不等待另一钱包；另一钱包仍按自己的缺口继续激活策略。该模式允许单轮预计 PAPER 低于质押门槛。由于未来铸币率和亏损侧不确定，目标是动态估计而非到账保证。

双边实际开仓价差上限现为 **3 bps**（`maxEntryGapBps`）。持仓的触发条件为「从两边开仓均价移动的绝对幅度 > 本轮动态基础平仓阈值 + 两边实际开仓价差」；加的是实际价差，不是固定 3 bps，计算使用整数精度，不提前取整。开仓前按允许的最大 3 bps 预留强平缓冲，成交后按实测价差复核；超过 3 bps 或缓冲不足则双边退出并暂停新仓。旧轮次保存的基础阈值不改，重启后按同样公式计算。

已有一个钱包质押、另一个尚未质押时，继续按**未质押钱包当前 PAPER 余额**计算达到单钱包质押目标的最小安全阈值，基础下限 15 bps。两个钱包都质押后，当前模板启用 `costModeObjective: "throughput"`：在成本上限内优先提高每小时新增 PAPER，而不是仅选单位成本最低的档位。

效率模式对 25～100 bps 每档评估两边实际开仓价、全额开仓价差补偿、盈利扣减、当前铸币曲线和强平缓冲，先找当前曲线下最低单位成本，再允许候选单位成本最多高 25%；按真实持仓年龄在 180 分钟内平滑放宽到 30%，不会因重启重置。候选通过成本边界后，按 `预计 PAPER /（剩余触价等待 + 平仓结算等待 + 下轮开仓等待）` 排序，另对到账未满单钱包质押门槛的分批等待施加小幅惩罚。两个钱包 PAPER 从不合并；报告逐钱包列出继续质押所缺 PAPER、预计亏损轮数和批次等待，损失分配按两种方向均衡估计，不保证交替发生。

行情使用 BTC 的 5／15／60 分钟收益波动、15 分钟实际区间及趋势效率，保留当前价格距原开仓均价的位移，修正简单扩散等待模型。平仓延迟取最近 8 个正常结算轮次从**第一次平仓请求**到最后结算的中位数，并加上四分之一的 P90 尾部延迟；包括签名过期／续签等待，不只统计最后一次请求。历史等待是估计，不保证未来结算时长。协议铸币率每分钟留样，至少 5 分钟有效样本后才外推其下降趋势，最多外推 6 小时；这只限制预测距离，不是平仓倒计时。样本不足时明确使用默认等待／零衰减预测，不编造历史。

`costModeMaxHoldMinutes: null` 保持关闭时间筛选；效率模式不因持仓时间到点直接平仓。仍需报价超过“动态基础 BPS + 实际开仓价差”才能策略平仓。持仓期间每秒重新评估，已接受的基础阈值只降不升；旧轮次保留原策略，必须显式 `optimize-close` 才切换到新效率策略。无新鲜 LP／BTC 样本、支付队列不清或无成本边界内安全候选时维持原退出目标，不猜测改档；开始平仓后不再改目标。

只要还有钱包未质押，持仓超过 `slowCloseAfterMs: 30000`（从双边成交较晚时间算起），且最近 60 秒报价样本覆盖至少 30 秒、波动区间不高于 `lowVolatilityRangeBps: 12` 时，开始降档：先允许 10 bps；此后每隔 `slowCloseStepMs: 180000` 再放宽 2 bps，最低 8 bps。若持仓超过 `slowCloseForceAfterMs: 300000` 仍未平仓，也允许进入降档评估，不再依赖低波动判定。每个候选档分别检查**每个未质押钱包**按实时铸币曲线达到 105% 目标所需的亏损侧结算次数（最多 `slowCloseMaxLosses: 6`），并按最慢钱包估算累计净成本；只有累计成本不超过正常档的 150%（`slowCloseCostToleranceBps: 5000`）且保有强平缓冲时才降档。已接受的平仓目标在该轮只会下降，不因短时波动或重启而回升。达到官方实际质押门槛的单个钱包仍立即质押。**新模板 `autoClaim: false`，仍自动质押，但不自动领取分红。**

以下 25／50／100 bps 表格只适用于旧 `lpDynamic` 模式，不适用于新模板：

默认每 1 秒读取 LP。独立轮询任务不等待交易 HTTP 请求完成，避免开平仓请求拖慢 LP 更新；请求超时或限流时按实际网络与 Retry-After 退避，不并发堆积请求。使用接口链索引时间判断新鲜度，超过 30 秒、时间异常或索引回退不放行新仓。

交易状态刷新、交易 HTTP 回执、历史补账和持仓期间的授权续期不再阻塞持仓检查。LP 读取失败、索引回退或时间异常会立即标记为不健康，不能用尚未过期的旧缓存继续开仓；收到不低于已持久化索引的有效新快照才恢复。存量退出不受 LP 健康门槛阻挡。

完整双边对冲持仓若报价、交易状态或任一钱包实时快照短暂中断，先进入 `hedged_data_degraded`，暂停使用旧报价触发策略平仓；恢复时输出 `hedged_data_restored`。超过 `hedgedDataGraceMs: 15000` 毫秒仍未恢复才输出 `hedged_data_timeout` 并退出存量仓位。开仓中的短暂数据中断同样先等待该宽限期，分别记录 `opening_data_degraded`／`opening_data_restored`；持续中断才取消旧请求并退出已成交仓位。若确认两边均未成交、旧请求均已终结且实时账户无仓位，冷却 30 秒后自动重新检查，不会因空轮次永久停机；任何一侧已成交仍按原风控退出。新一轮开仓仍要求 5 秒内的新鲜报价和交易状态。断点保留中断时各数据年龄、钱包连接状态及交易接口错误，供只读排查。BTC BBO 使用 WebSocket；连接在线但 BBO 静默 7 秒时重新订阅，15 秒仍无新报价则断开重连。钱包状态使用官方 SSE 自动重连；交易状态与 LP 仍使用官方只读 HTTP 接口。

| 阶段 | 初始平仓阈值 | 条件 |
| --- | --- | --- |
| 激活质押 | 最低从 25 bps（0.25%）起，每 1 bps 上调 | 两钱包都没有已质押 PAPER |
| 手续费阶段 | 最低从 50 bps（0.5%）起，每 1 bps 上调 | 已有质押，但未达到下述盈余条件 |
| LP 盈余阶段 | 100 bps（1%） | tracked LP 达到接口的分配上限，并观察到手续费收入或协议待分配收益 |

首次和 tracked LP 低于平坦区阈值时，优先使用最低名义本金，目前为每边 10,000U。自动杠杆每轮根据两个钱包各自的可交易余额计算：先排除预留分红和 queued，再应用资金上限、保证金利用率与保证金上限，取较小的钱包预算匹配两边相同杠杆及名义本金。默认利用率 66.67%。

例如另一侧资金充足时，较少一侧可交易余额为 500U → 31 倍、每边约 322.58U 保证金；450U → 34 倍、约 294.12U；400U → 38 倍、约 263.16U；350U → 43 倍、约 232.56U；300U → 50 倍、200U；250U 需要约 60 倍，超过新配置上限，所以暂停新开仓并继续奖励监控。杠杆会随资金恢复而下降，但不得超过配置或市场上限；如果当前平仓目标无法保留强平缓冲，则暂停，而不是继续提高杠杆。每个钱包的余额、保证金预算、所需杠杆会出现在策略报告中。

- 同时读取 LP 现金、tracked LP、tailProgress、铸币参数和支付队列，不把 TVL 等同于 LP。
- 当前质押目标为实时最低质押量的 **105%**（`stakeTargetBps: 10500`）。每轮开仓前按实时铸币曲线在 **25～100 bps、每档 1 bps** 中选择满足目标的最小阈值；手续费阶段不低于 50 bps，LP 盈余阶段为 100 bps。估算时扣除允许的最大开仓价差对亏损侧的不利影响，并把两钱包较少侧未质押余额计入。若仍不足或强平缓冲不够就暂停新仓，不靠增加杠杆补足。
- 当前模板每个目标都要求至少 50 bps 强平缓冲，不主动追求爆仓；旧配置缺省仍为 20 bps。
- 已经开仓的轮次继续使用其持久化阈值；例如已有轮次的 50 bps 不因更新质押目标而被覆盖。如果一侧 PAPER 到账并自动质押，下一轮默认进入手续费阶段，基础阈值仍是 50 bps；105% 目标只决定是否需要在此基础上再上调。
- 协议支付队列或本账户排队盈利非零时暂停新仓；存量按原目标处理，已有 PAPER 仍可质押。
- 新仓还须通过 OI 安全余量检查：当前模板在 BTC 净 OI 上限和多、空方向仓位上限之外各预留折合 **500,000 USDC** 的空间，并要求至少 **5 个不同交易状态区块、持续 5 秒**均满足条件。签名后仍按最新状态复检。先向 OI 余量更紧的一侧提交开仓：若官方立即明确以 `openInterest` 拒绝，另一侧不会提交，并冷却 **2 分钟**后重新检查；先导侧获接收后才提交另一侧。交易所两笔准入不是原子操作，安全余量和分阶段提交不能保证两边同时成交；若第二侧被拒或先导回执不明，仍退出已成交脚本仓位。
- 已积累 LP 的阶段，预测单笔盈利支付最多使用报告 LP 现金的 10%（`lpPayoutFractionBps: 1000`）；必要时缩仓，但不低于最低名义本金。零 LP 自举阶段允许最低规模的开仓。
- 仓位不超过配置的保证金、杠杆范围、资金上限和两钱包可用余额；不使用 queued 保证金。
- 旧 `lpDynamic` 模式的阈值开仓前确定并持久化，持仓途中不自动修改；新 `lpAccumulating` 模式只动态修改已对冲轮次的平仓阈值，杠杆和保证金仍保持开仓时的值。重启保持断点；旧版无策略记录的存量轮次按原 100 bps 处理。
- 默认逐轮交替 A/B 多空方向，缓解持续行情中的余额偏移，但不能保证消除失衡；没有方向预测或 Hyperliquid 下单功能。

这些是可执行的初始规则，不是已验证的最优阈值。预测使用文档手续费和当前参数，实际损耗、PAPER 和分配以链上结果为准。

## 3. 到账即质押、分配独立领取

两钱包各有独立奖励任务。账户 SSE 确认 PAPER 到账后唤醒任务，不等待另一侧平仓 HTTP 请求完成或下一轮交易。达到实时最低质押量就签署 `Stake`，低于门槛的余额保留到足够再处理。

奖励任务只检查对应钱包的连接状态；另一钱包断线或尚未获得快照不会阻止健康钱包质押和领取。丢失 HTTP 回执时，可在账户已索引区块通过 `eth_call` 读取 `isNonceUsed`，结合对应账户实际质押／领取变化确认奖励结果；单独看到 nonce 已使用或余额变化均不视作成功。

交易用 session key；**质押和领取由主钱包签名**，使用已核验的 PaperStaking 地址和签名域。主钱包私钥不写入数据库，Paper 和 Exchange nonce 独立持久化。

仅在 `autoClaim: true` 时通过链上 `PaperStaking.pendingReward(address)` 只读调用获取真实可领取 USDC；新模板为 `false`，不提交领取请求。若以后手动开启，默认每 1 秒检查，达到 `minClaimUsdc: "0.01"` 才领取到交易所可用余额。未知、超时请求保留状态，不盲目换 nonce 重下。

`keepRewardsMonitoring: true` 时，交易达到轮数、启用的损耗限制或发生恢复退出后，停止新交易但继续奖励任务。余额不足、LP 不满足开仓条件也不影响奖励监控。显式 `stop` 停止全部新任务。

新模板仍保留 `reserveClaimedRewards: true`：若以后领取了 USDC，实际领取金额作为逻辑预留，不再投入下一轮交易。资金仍在你账户内，脚本不锁定或转移它；检测到手动提现时按收益优先消耗预留。旧配置默认不启用此项。

资格从质押链上确认后开始，已完成的分配不能追溯领取。脚本不调用 keeper 专属分配路径，不保证抢在某次分配前确认。**不自动提现、不调拨两钱包本金。** 领取后的 USDC 在交易所内，提现由你操作。

## 4. 配置与报告

### Bark 手机通知

在本地 `.env` 配置 `PAPERTRADE_BARK_URL` 为完整的 HTTPS 设备 URL；设备密钥不写入数据库或日志。脚本对每轮的**开仓提交、双边成交确认、平仓提交、双边结算**分别推送。消息包含两钱包 USDC 总额／可用／锁定、轮次两边合计 PNL、本轮已结算 PAPER、两钱包未质押／已质押 PAPER、累计已领分红，以及链上只读查询的当前可领取 USDC；所有金额四舍五入显示两位小数。通知异步发送，失败保留在断点中退避重试，不阻塞交易；`autoClaim: false` 时仍可只读展示分红，但不会领取。

开仓前若任一账户的可用资金不足以满足目标名义仓位、配置杠杆和强平缓冲，脚本会阻止新仓并推送 Bark 保证金预警，列出目标、所需可用余额及每个钱包的缺口；相同风险状态最多每 30 分钟提醒一次。该预警不自动提现、跨链或在钱包之间转账；脚本停止时不执行检查或推送。

## 5. 恢复、兼容与验证

保留 `data/`，用相同钱包顺序和市场重启。有仓位或未知请求时不要删除数据库。旧状态库可继续使用，旧轮次不会被新阈值覆盖；旧配置省略新字段时保持固定模式，不自行启用质押/领取，采用新策略需更新配置。

### 断点状态读取

```bash
npm run bot:checkpoint
# 或使用其他状态目录
npm run cli -- checkpoint --state-dir ./data
```

此命令不需要 `.env`、不连接交易所、不签名，只从状态数据库读取：未完成轮次及两侧请求状态、已确认仓位 ID、冻结的轮次策略、待确认质押／领取、nonce 游标、奖励预留、本地账户快照及最近一次运行阶段。输出**不包含私钥、加密 session 内容或已签请求正文**；本地余额明确标记为历史快照，不替代官方实时余额。

启动 `run --live` 时先读取并校验断点，记录 `checkpoint_loaded`；运行时每秒更新 `runtimeCheckpoint`，阶段变化时输出 `checkpoint_progress`，`status` 也会显示恢复进度。断点不完整或钱包、轮次关联不一致时直接拒绝继续，避免错误关联旧仓位。官方账户 SSE 和链索引仍是执行结果的权威来源，**断点本身不能证明成交**：

后台 nonce 证据只针对当前未完成轮次的已过期开仓及真正待确认的请求读取；已经完成的历史轮次不再每 5 秒重复发起 RPC。RPC 暂时不可用时记录 `nonce_evidence_unavailable`（含钱包、动作和轮次），保持未知请求待核对，不把读不到证据当成成交失败。已经确认的双边持仓仍按冻结策略监控。

- 双方开仓请求都已提交：保留原请求 ID，等待实时账户同步；重启不重签、不补发第二个开仓请求。
- 有从未提交的预备开仓：本地取消该预备请求，进入存量退出，不盲目补对冲。
- 已对冲或待平仓：沿用历史仓位 ID 和原轮次阈值，只在官方账户状态同步后处理；待平仓请求不因重启而自动撤单。
- 原状态为 `recovering`、或有未核实仓位归属：保留停止新交易的状态，继续核对或退出；奖励任务遵照当前配置独立监控。

再次执行 `npm start` 表示明确启动新进程；如果上次已完全退出且没有待核实仓位，原停止请求会清除，重新按实时条件计算下一轮。状态库必须保留，不能用删除 `data/` 来“重置”未知请求。

### 手动热更新当前轮次阈值

切换双质押持仓为成本边界内的效率模式，先预览，再确认（把 58 换成实际活动轮次）：

```bash
npm run bot:optimize -- --round 58
npm run bot:optimize -- --round 58 --confirm-retarget
```

该命令计算动态候选并检查真实仓位、成本边界、强平缓冲和最新 BBO，不签名或重新开仓，只事务性更新该轮次策略并记录审计。不允许抬高现有阈值；如果当前报价已越过新阈值，默认拒绝，必须明确添加 `--accept-immediate-close`。启用新的引擎代码需要断点恢复重启；不应使用 Ctrl+C 来“保留仓位重启”，因为 Ctrl+C 原有语义是退出存量仓位。`status` 的 `liveCloseDecision` 和本轮 `closeEfficiency` 可查看成本上限、单位成本、小时产出模型、队列样本和逐钱包批次预测。

运行中的进程不会热加载配置文件，但会在每次持仓检查时读取持久化轮次。先只读预览，再由操作者显式确认；命令只修改该轮次保存的平仓阈值，不签名、不提交订单：

```bash
npm run bot:retarget -- --round 18 --close-bps 30
# 只有预览显示 allowed: true，且确认接受可能立即触发平仓时，再手动执行：
npm run bot:retarget -- --round 18 --close-bps 30 --confirm-retarget
```

命令核对轮次 ID、原阈值、双方仓位、运行中的账户数据、最新 BBO、强平缓冲及按实时铸币曲线计算的 105% 质押目标；若当前报价已越过新阈值，默认拒绝，只有显式添加 `--accept-immediate-close` 才允许。事务内再次检查轮次状态，记录原／新阈值、行情和协议区块。仅支持降低仍在 `hedged` 状态的 LP 动态轮次阈值；开始平仓、账户断线或轮次变化都会拒绝。成功后旧进程在下一次读取该轮次时使用新阈值，无需重启；若行情在检查期间变动，新阈值可能随即触发平仓。

如果开仓成功和强平均发生在断线期间，且本地从未取得 position ID，会主动查询历史。**当前公开历史接口未保证提供开仓 intentId 关联**：只有权威记录包含可核验的 `openIntentId`，且方向、市场、金额及杠杆均匹配，才自动补记；否则明确暂停新交易，在 `status.unresolvedOwnership` 中提示需要核实的请求，不按相似金额／方向／时间猜测接管。该极端场景仍可能需要人工补充官方回执信息，并非已经实现无条件自动恢复。

session 用 HKDF + AES-256-GCM 加密保存；数据库权限 `0600`、目录 `0700`。短期签名请求用于恢复，不输出到日志。`.env`、`config.json`、`data/` 均在 `.gitignore` 中。

```bash
npm run typecheck
npm test
npm run build
# 公共只读接口、零地址 SSE/BBO/pendingReward，不读取私钥
npm run check:read
```

开发验证只有模拟和公共只读接口，未提交真实授权、交易、质押或领取。最近只读检查中官方仍暂停 `openPosition`；运行前以 `preflight` 返回的实时状态为准。
